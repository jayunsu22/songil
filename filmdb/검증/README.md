# 설계 7-2 — 사진 매칭 정확도 측정

정답(필름 코드)을 아는 사진으로 실제 검색을 돌려, **정답이 몇 등에 오는지** 잰다.
지금까지 매칭 가중치들은 근거 있는 시작값일 뿐 실사진으로 검증된 값이 아니었다.

## 사진

`D:\n8n_1분견적(필름)\검증사진\` 에 샘플북 쪽 사진을 넣는다.
쪽마다 실린 코드는 `쪽목록.js` 에 읽는 순서(위→아래, 왼→오른쪽)대로 적는다.

## 순서

```
node 검증/점만들기.js    # 색판 중심 좌표를 찾아 점.json 으로 저장
node 검증/보고.js        # 적중률 (전체·쪽별·카테고리별)
node 검증/진단.js        # 사진색이 DB색에서 어느 방향으로 어긋나는가
node 검증/분해.js        # 오차 중 보정 가능한 몫과 남는 몫
node 검증/천장.js        # 카메라 보정이 완벽했다면 몇 %인가
node 검증/쓸기.js        # 상한·대비가중치를 바꿔가며 적중률 비교
```

`격자시험.js` 는 찾은 색판 위치를 사진 위에 코드와 함께 그린다.
**자동 검출을 믿지 말고 이 그림을 눈으로 확인한 쪽만** `점만들기.js` 의 `확인됨` 에 넣는다.

## 색판 위치를 어떻게 잡는가

흰색 페이지는 색판과 종이의 밝기 차가 15 이하라 자동 검출이 16개 중 6개밖에 못 잡는다.
그래서 두 단계로 한다.

1. `색판찾기.js` — 조명 기울기를 2차 곡면으로 보정하고, 침식으로 붙은 색판을 떼어 낸 뒤 연결 요소를 찾는다
2. `격자.js` — 잡힌 몇 개로 (칸,줄)→(x,y) 아핀 격자를 역산해 **놓친 칸까지 채운다**

`측정.js` 는 앱(`film_app.js`)과 똑같은 순서를 밟는다.
EXIF 회전 → 긴 변 1400 축소 → 반지름 폭×3.5% 의 원 → `영역색()` → `M.검색()`.
이 순서가 어긋나면 측정값이 앱의 실제 동작과 달라진다.

## 2026-09-06 측정 결과 (영림 샘플북 8쪽, 87건)

| 조건 | 5위 안에 정답 | 30위 안에 | 사진색 ΔE 중앙 |
|---|---|---|---|
| 예전 설정 (보정 없음, ΔE 상한 5) | 5.7% | 10.3% | 8.41 |
| **지금 배포된 설정** | **14.9%** | **39.1%** | **6.52** |
| 카메라 보정이 완벽했다고 가정 | 46.0% (우드 67~83%) | 74.7% | 3.71 |

배포 설정: 흰점 보정 + 노출 맞춤(기준 245) + 검은점 빼기, **세기 0.6**, ΔE 상한 12.

**세기를 1.0 이 아니라 0.6 으로 둔 이유** — 건별 ΔE 변화로 골랐다.
상위5위 적중률은 n=87 에서 한 건이 1.1%p 라 노이즈가 크지만, 아래 숫자는 안정적이다.

| 세기 | 전체ΔE | 우드ΔE | 좋아짐 | 나빠짐 | **크게 나빠짐(+2 이상)** |
|---|---|---|---|---|---|
| 0.4 | 6.98 | 8.22 | 86% | 8% | **0%** |
| 0.6 | **6.52** | **8.16** | 83% | 11% | **0%** |
| 0.85 | 6.58 | 8.36 | 76% | 18% | 5% |
| 1.0 | 6.58 | 8.74 | 74% | 20% | **10%** |

끝까지 되돌리면 열 건 중 한 건을 크게 망친다. '가장 밝은 것은 완전한 무채색' 이라는
가정이 늘 조금 틀리기 때문이다(종이·흰 벽에는 형광증백제가 들어 있어 원래 푸르스름하다).

- 사진색과 DB색의 ΔE 중앙값 **8.41** — 87건 중 74건이 ΔE 상한 5를 넘어 후보에서 아예 빠졌다
- b\* 가 94% 같은 방향으로 −7.75 치우쳤다 → 자동 화이트밸런스
- L\* 는 쪽마다 −14 ~ +11 로 흔들린다 → 자동 노출
- `kL=2` 는 L\* 만 눌러준다. 정작 가장 일관되게 틀리는 축은 b\* 다
- `대비가중치` 0.15 ↔ 0 은 결과를 거의 바꾸지 않는다 — 병목이 아니다

메탈·채도 높은 색은 샘플북 인쇄가 원본 색을 못 따라가므로(오프셋 인쇄 색역)
그 쪽 숫자는 도구가 아니라 시험지 탓이 섞여 있다.

## 이 시험지로는 우드를 못 잰다

우드는 어떤 설정에서도 상위5위 4.2% 에 머문다. 원인을 따로 확인했다.

- **DB 결함이 아니다.** 영림 우드가 타 브랜드 우드에 대해 갖는 최근접 ΔE 중앙값은 1.33 으로
  다른 브랜드(1.06~1.33)와 같은 수준이다. 영림 색이 따로 놀지 않는다.
- **샘플북 인쇄가 원본보다 덜 노랗다.** 보정 전 우드의 b\* 편차가 -11 근처였다.
  진한 갈색은 CMYK 색역 밖이라 오프셋 인쇄가 못 따라간다.
- 쪽 단위 최적 보정을 씌우면 우드 ΔE 가 1.4~2.2 까지 떨어진다.
  즉 인쇄본과 DB 는 **일정한 변환 관계**에 있다 — 재현 방식이 다를 뿐 무작위 오차가 아니다.

실제 필름(PVC 실물)을 방에서 찍은 사진은 세 번째 재현 방식이라 이 숫자와 다를 것이다.
**이 시험지로는 그 값을 알 수 없다.** 알려면 코드를 아는 시공 현장 사진이 필요하다.

## 브라우저 시험이 잡은 버그 (측정으로는 못 잡았다)

검은점 추정에 상한이 없었다. 짙은 갈색 문짝이 화면을 가득 채운 사진에서는
'가장 어두운 화소' 가 번진 빛이 아니라 문짝 자체라서, 그걸 빼면 문짝이 새까매진다.
브라우저에서 합성 사진으로 시험하다 `#000000` 이 나와서 발견했다.

검증 사진 14장이 모두 책상·배경이 함께 찍혀 있어서 **측정에서는 절대 드러나지 않는 버그**였다.
테스트셋이 한쪽으로 쏠려 있으면 그 쪽에서만 안전한 코드가 통과한다.
